The 30-second pitch

Use this for "Tell me about a project you've built."

Say this

"I built QuizApp, a full-stack MERN quiz platform for teachers and students. Teachers organise students into batches, create multiple-choice quizzes with explanations, and set a deadline and time limit. Students take timed quizzes that are scored on the server and see the correct answer and explanation for every question. Teachers follow results on a dashboard and a leaderboard they can export to Excel. I used JWT auth in httpOnly cookies with role-based access, MongoDB for storage, Redis caching for dashboards and leaderboards, Swagger for API docs, and Docker to run the whole stack."

The 2-minute walkthrough

Use this when they say "walk me through it". Follow this order: problem → users → architecture → one interesting detail → result.

1 · Problem

Writing quizzes and grading them takes teachers a lot of time, and students usually get a score without understanding their mistakes.

2 · Users & features

Two roles. Teachers create batches and quizzes, and watch a dashboard and leaderboard with Excel export. Students join batches, take timed quizzes and review their results.

3 · Architecture

A React + Vite SPA calls an Express REST API. Data is in MongoDB through Mongoose: Users, Batches, Quizzes with embedded questions, and Results. Redis caches read-heavy endpoints.

4 · Interesting detail

Pick one: server-side scoring with a unique index to prevent double submission, hiding correct answers from every student-facing endpoint, or cache invalidation with key patterns.

5 · Quality

Role-protected routes on both client and server, answers never sent to students, Swagger docs, Docker Compose, and an end-to-end test of the main flows.

6 · What I learned

Designing APIs around who should see which data, the cookie and CORS rules for cross-site auth, and keeping a cache consistent with the database.

Tip: Stop after 2 minutes and let them pick what to dig into. Don't quote performance numbers you haven't measured. If asked, explain how you would measure, for example timing an endpoint with and without the cache.

Key request flows

Interviewers love "what happens when…" questions. Know these three.

1. Login and staying logged in

POST /api/auth/login→bcrypt.compare→jwt.sign({userId, role}, 1d)→Set-Cookie: token (httpOnly)

On every page load, AuthContext calls GET /api/auth/check. The verifyToken middleware validates the cookie and the API returns the user and role. ProtectedRoute then lets the user in or redirects to /login or to the user's own dashboard.

2. Creating a quiz

POST /teacher/create-quiz→verifyToken + requireRole('teacher')→validate questions→batch owned by teacher?→Quiz.create→invalidate caches

Each question needs text, at least two non-empty options and a valid correct-option index. Questions are embedded in the quiz document. After saving, the API deletes teacherQuizzes:<id> and student:*:batch:<batchId>:quizzes so the teacher and every student in the batch see the new quiz immediately.

3. Taking and submitting a quiz

GET /student/quiz/:id→member? not submitted? before deadline?→questions without answers→timer→POST /student/submit→score on server→Result (unique quiz+student)→invalidate caches

The client sends only {questionIndex, selectedOption} pairs and the time spent. The server recalculates the score, updates the quiz's average with an aggregation, and deletes the affected cache keys: student results, the student's batch list, and the teacher's leaderboard (leaderboard:<teacherId>:*).

Design decisions you can defend

For each one, say what you chose, why, and the trade-off.

JWT in an httpOnly cookie

JavaScript can't read it, so an XSS bug can't steal the token. Over HTTPS it's SameSite=None; Secure (frontend and backend are on different domains), and over local HTTP it's Lax. Trade-off: cross-site cookies need careful CORS (credentials: true plus an explicit origin list) and CSRF awareness.

Score on the server

Never trust the client. If the browser sent a score, anyone could post 100%. Correct answers are stripped from every student-facing response until after submission.

Embed questions in the quiz

A quiz and its questions are always read together and are bounded in size, so embedding means one read and no joins. Results are a separate collection because there are many per quiz and they grow without limit.

Unique index (quiz, student)

An application-level "already submitted?" check has a race condition when two requests arrive together. The database index guarantees a single attempt, and the duplicate-key error (11000) is turned into a 409.

Cache-aside with targeted invalidation

Read the cache, fall back to MongoDB, and store with a TTL. Writes delete exactly the affected keys or patterns. TTLs are a safety net. Redis is optional, and the app falls back to an in-memory cache so local setup stays simple.

Status computed, not stored

"Available", "completed" and "overdue" are worked out on each request from the deadline and the student's results, instead of being saved. Nothing can go out of sync, and a quiz becomes overdue the moment its deadline passes without any background job.

Role checks on both sides

ProtectedRoute on the client is for UX only. Real security is verifyToken + requireRole applied to every route of the student and teacher routers.

Swagger from JSDoc

The docs live next to the routes, so they stay in sync. They're also handy for demos and for frontend work in parallel.

Challenges and bugs I fixed

Real problems from this codebase. Use one as a STAR answer to "Tell me about a difficult bug."

STAR example: "users got logged out on every refresh"
Situation
After login everything worked, but refreshing any page sent the user back to the login screen. Registering didn't log you in either.
Task
Find out why the session wasn't restored even though the cookie was valid.
Action
I traced the startup flow. The frontend checked res.data.success, but the API returned {valid: true}, so it always treated the user as logged out. Register also never set the cookie. I made /auth/check return the user and role, stored the user in AuthContext, added a role-aware ProtectedRoute, and issued the cookie on register too.
Result
Sessions survive refreshes, users land on the right dashboard for their role, and I added an automated browser test covering register → refresh → still logged in.
Student-facing endpoints returned full question objects, including correctAnswer, visible in DevTools.
Return only questionCount in lists. The quiz endpoint returns only question text and options.
The app crashed at startup if one hardcoded Redis Cloud server was unreachable, and its password was committed in the code.
Moved to a REDIS_URL env var with a limited reconnect strategy and an automatic in-memory fallback. The leaked password needs rotating.
client.del('leaderboard:id:*') doesn't support wildcards, so leaderboards stayed stale.
Added delPattern(): find the keys matching the pattern, then delete them.
The teacher dashboard counted only students in batches that already had quizzes, and averaged in quizzes nobody had taken (0%).
Count unique students across all the teacher's batches, and average only quizzes with at least one submission.
Quiz timer recreated its interval every second and called submit inside a state updater, which risked double submission.
One interval, a separate effect submits at 0, and a ref guard plus the DB unique index stop duplicates. Real time spent is recorded.
Picking a leaderboard filter emptied the other dropdown, because the API returned no options when a filter was applied.
The API always returns all of the teacher's batches, plus that batch's quizzes.

What I'd improve next

Always have an answer to "What would you do with more time?"

  • Tests in CI: Jest + Supertest for the API, Playwright for the UI, running on every push.
  • Security hardening: rate limiting on login (express-rate-limit), helmet, input validation with zod or express-validator, CSRF tokens for the cross-site cookie setup.
  • Server-side timer: store startedAt when a quiz is opened, so a student can't extend time by reloading.
  • Question bank and randomisation: shuffle questions and options per student to reduce copying.
  • Scale: paginate leaderboards and results, and use SCAN instead of KEYS for cache invalidation.
  • Features: password reset by email, editing quizzes after publishing, per-question analytics for teachers, and more question types (multi-select, true/false).

No questions match.

Why did you build this project?Project

To solve a real classroom problem: running and grading quizzes takes teachers a lot of time, and students rarely get explanations. It also let me practise a complete production-style stack: auth with roles, a relational-style data model in MongoDB, caching, API docs and Docker.

What was the hardest part?Project

Cross-site cookie auth between the two Render domains. Logins worked locally but not in production until I understood SameSite=None; Secure, trust proxy and CORS with credentials. A close second was keeping the Redis cache consistent: deciding exactly which keys each write must delete.

How do teachers and students see different things?Project

The JWT carries the user's role. On the server, the student router uses verifyToken, requireRole('student') and the teacher router uses requireRole('teacher'), so every endpoint is protected. On the client, ProtectedRoute sends users to their own dashboard. The server checks are the real security; the client checks are only for UX.

How do you stop a student from cheating?Project

Correct answers are never sent before submission. Scoring happens on the server. A unique index allows only one attempt per quiz, and the server checks batch membership and the deadline. To go further, I'd add a server-side timer (store startedAt), randomise question and option order per student, and log tab switches.

How is authentication state handled in React?React

An AuthContext provider wraps the app. On mount it calls /auth/check and stores user (or null), and it shows a loader until that finishes so routes don't flash. login() and logout() update the context. The token itself is never in JavaScript because it's an httpOnly cookie; Axios sends it automatically with withCredentials: true.

How does the quiz timer work, and how do you avoid double submission?React

When the quiz loads I start a single setInterval that decrements timeLeft. A separate useEffect watches timeLeft === 0 and calls handleSubmit. Submit uses a useRef flag so the button and the timer can't both fire, and it reads the answers from a ref to avoid stale closures. The database unique index is the final guarantee.

How does the Excel export work?React

It happens fully in the browser. The leaderboard rows already loaded from the API are mapped to plain objects (rank, name, email, quiz, score, time), turned into a sheet with SheetJS json_to_sheet, and downloaded with writeFile. No extra server endpoint is needed.

Why Context instead of Redux?React

The only truly global state is the logged-in user. Everything else is page-level server data fetched with Axios. Context is enough and avoids boilerplate. If the app grew, I'd add React Query or TanStack Query for server-state caching rather than Redux.

What does useMemo do on the student dashboard?React

It derives the stats (completed count, active count, average score) from the quizzes-by-batch data and only recalculates when that data changes, not on every render.

Explain the Express middleware chain for a protected request.Node / Express

express.json() parses the body, then cookieParser() exposes req.cookies, then cors() sets the headers. On the router, verifyToken verifies the JWT and sets req.user, requireRole checks the role, and validateIds rejects bad ObjectIds with a 400 before the controller runs. A final error handler turns unexpected errors, such as invalid JSON, into JSON responses.

Which HTTP status codes do you use and why?Node / Express

201 for creation, 400 for invalid input, 401 for a missing or invalid token, 403 for wrong role or not a batch member, 404 for not found, and 409 for conflicts (duplicate email, already submitted). Accurate codes let the frontend react correctly, for example redirecting to the result page on a 409.

How did you document the API?Node / Express

With swagger-jsdoc: OpenAPI comments sit above each route, and swagger-ui-express serves them at /api-docs. Cookie auth is declared as a security scheme.

Describe your MongoDB schema.MongoDB

Four collections. User (unique email, role, batch refs). Batch (teacher ref, student refs, so it's many-to-many with users). Quiz (batch and creator refs, with embedded questions: text, options, correct index, explanation). Result (quiz and student refs, score, answers). Questions are embedded because they're always read with their quiz and are bounded. Results are referenced because they grow without limit.

Which indexes did you add and why?MongoDB

On Result: {quiz, student} unique (one attempt, plus fast lookups) and {student, completedAt: -1} for "my results". On Quiz: {createdBy, createdAt: -1} for the teacher's list and {batch, deadline} for student batch views. On Batch: {students} for membership queries. User has a unique index on email.

Why keep batch membership on both User and Batch?MongoDB

It's denormalised for fast reads in both directions: a student's batches for the dashboard, a batch's students for the teacher. To keep the two in sync I use $addToSet and $pull updates on both documents. In a bigger system I'd wrap the two updates in a transaction.

How do you calculate the average score of a quiz?MongoDB

After each submission, an aggregation ($match on the quiz, then $group with $avg) recalculates it, and it's stored on the quiz as avgScore so dashboards don't need to aggregate on every read.

What's the N+1 query problem? Did you hit it?MongoDB

It means running one query per item in a list. The batch-quizzes endpoint originally ran one Result.findOne per quiz. I replaced it with a single Result.find({quiz: {$in: ids}}) and a Map lookup.

Why httpOnly cookies instead of localStorage?Auth & Security

Anything in localStorage can be read by injected scripts (XSS). An httpOnly cookie can't be read by JavaScript and is sent automatically. The trade-off is CSRF risk, which is reduced by SameSite, a strict CORS origin list and JSON-only endpoints. CSRF tokens would be the next step.

Explain SameSite and why it changes between local and production.Auth & Security

In production the frontend and API are on different sites (two onrender.com subdomains, and onrender.com is a public suffix), so the browser only sends the cookie with SameSite=None, and that requires Secure (HTTPS). Locally, localhost:5173 and localhost:5000 are the same site over HTTP, so Lax without Secure is used. The server picks automatically using req.secure with trust proxy enabled.

How are passwords stored?Auth & Security

Hashed with bcrypt at cost factor 10. bcrypt adds a random salt and is deliberately slow, which makes brute-forcing hard. Login returns the same "Invalid email or password" for both cases, so attackers can't find out which emails are registered.

What is CORS and how did you configure it?Auth & Security

Browsers block cross-origin requests unless the server allows them. I use the cors package with an explicit list of allowed origins (extendable with CLIENT_URLS) and credentials: true. A wildcard * isn't allowed when credentials are used.

Did you find any security issues in your own code?Auth & Security

Yes. A Redis password was hardcoded in the repo (moved to env; it should be rotated), some routes were missing role checks, and student endpoints leaked correct answers. All are fixed. It taught me to review what each endpoint returns from the point of view of who calls it.

Why Redis, and what do you cache?Redis

These endpoints are read far more often than they change: the batch list, a teacher's quizzes, a student's batch quizzes, results and leaderboards. Each key has a TTL (5 minutes to 1 hour), for example leaderboard:<teacherId>:<batch>:<quiz>.

How do you keep the cache consistent?Redis

Cache-aside with invalidation on write. Creating a quiz deletes teacherQuizzes:<id> and student:*:batch:<batchId>:quizzes. Submitting deletes the student's results and that teacher's leaderboard keys. The TTL is a fallback in case a deletion is missed.

What happens if Redis goes down?Redis

The cache wrapper checks isReady. If Redis isn't available or a command fails, it uses an in-memory Map with TTLs, so the app degrades gracefully instead of crashing. With several server instances the memory caches would differ, which is why Redis is used in production.

Is using KEYS for pattern deletion OK?Redis

It's fine at this scale, but KEYS blocks Redis while it scans every key. In production I'd use SCAN iteratively, or track keys in a Redis Set per batch or teacher so invalidation is a direct lookup.

How is the project deployed and run?DevOps

The frontend and backend run as separate services on Render, with MongoDB Atlas and Redis Cloud. Locally, docker compose up starts the backend, MongoDB and Redis, plus an nginx container that serves the React build and proxies /api to the backend. Because that proxy makes everything same-origin, there are no CORS issues in Docker.

Why a multi-stage Dockerfile for the frontend?DevOps

Stage one uses Node to install dependencies and run vite build. Stage two copies only dist/ into a small nginx image. The final image has no node_modules or source code, so it's smaller and more secure.

How do you manage configuration?DevOps

Environment variables: MONGO_URI, JWT_SECRET, REDIS_URL, and VITE_API_URL at build time. A committed .env.example documents them, and the real .env is gitignored. dotenv/config is imported first so every module sees the values.

How do deadlines and durations work together?Project

The deadline is when a quiz stops accepting new attempts; opening it after that returns 403 and it shows as "overdue". The duration is the time limit once a student starts; the timer auto-submits at zero. A quiz with no deadline stays open. Today the timer runs in the browser; storing startedAt on the server would make it tamper-proof.

How did you test it?Project

An end-to-end API script covering register, login, role guards, batch join and leave, quiz create, submit and double-submit, results, leaderboard and delete. There's also a headless-browser (Playwright) run of the full teacher and student journeys. Next I'd move these into Jest + Supertest and Playwright test suites running in CI.

How would this scale to 10,000 students?Project

The API is stateless (JWT), so it can scale horizontally behind a load balancer, with a shared Redis. I'd paginate leaderboards and results, rely on the existing indexes, use SCAN for cache invalidation, and add rate limiting.
